# Minecraft API coverage

This is a source-based coverage matrix for the checkout at host **0.54.0**,
SDK/macros **0.52.0**, ABI **1.44.0**, Minecraft **1.21.1**, and NeoForge
**21.1.265**. It records the public surface that exists in this tree, its path
from a Minecraft hook to Rust/WASM, and the limits that remain. It is not a
roadmap or a claim of complete Minecraft mod compatibility. The matrix
tracks the current working tree. The verification section records which test
suites and in-game checks were executed for this checkpoint.

For guest-call rows, the Java host binds named WebAssembly imports through
`ModuleImports`,
which validates import names and signatures and exposes only bindings supplied
by the relevant host adapter. `AbiMemory`
and `AbiCodec`
bound and encode the byte boundary; domain-specific schemas/codecs are cited
where present. Rust `extern` imports and public wrappers are in the cited SDK
files. Registration callbacks and event-export callbacks use their own
documented ABI paths rather than a host import for every operation.

## Status definitions

- **Fully implemented** means the specifically named contract has a host
  implementation, a Rust-facing API where applicable, and tests for its
  boundary. It does not mean all of Minecraft's related features are covered.
- **Partially implemented** means usable end-to-end operations exist, but a
  significant part of the category requested below is absent or unverified.
- **Not implemented** means no public, vertical SJML API for that capability
  was found in the host/ABI/SDK path. A Minecraft resource file that happens to
  describe related data does not count as a runtime API.
- **Technically unsupported** means the current WASM/security architecture
  deliberately excludes the capability, rather than promising a future API.
- **Requires additional research** means this audit did not establish a safe,
  supported NeoForge extension point or a complete inventory for that area.

category counts, not percentages of Minecraft's total extension surface.

## What the evidence establishes

- This matrix is a source inventory; test paths identify coverage locations. The
  following verification record separately states which suites passed in this audit.
- Rust compilation and SDK contract tests establish guest-side validation,
  codecs, and wrapper behavior; they do not establish that a live game invokes
  the API. `sjml-core/src/test` primarily establishes portable ABI/runtime
  behavior; `src/test` establishes adapter logic under its fixtures.
- GameTests run against the NeoForge GameTest server and exercise live Minecraft
  host behavior for the listed server paths. Passing these tests does not prove
  display-backed rendering or a remote client/server session.
- The [compatibility record](COMPATIBILITY.md) leaves display-backed
  chat/render/GPU behavior and a real client/server network exchange
  unverified. Chat controller, theme, and routing tests prove contracts, not
  the visible behavior of Minecraft's client.
- The source tree includes a native chat layout and limited panel-theme API as
  of SDK 0.42.0/ABI 1.34.0, but no chat message-content API or replacement chat
  screen. This is a deliberate status distinction, not a claim that no chat
  work exists.
- On 2026-11-12, Gradle 9.2.1 completed `test build runGameTestServer`: 701 host tests and 289 `sjml-core` tests passed (990 reported, one core test skipped), and all 43 required GameTests passed. Live checks include villager trade-table insertion, incoming-damage veto, cross-dimension teleport into a loaded Nether chunk, shared game-time mutation, and the existing server API contracts. The CLI/SDK/macros workspace passed offline tests (24 CLI, 22 macro, and 202 SDK unit tests plus integration/doc tests), strict Clippy, and WebAssembly guest compilation; the examples workspaces also passed offline tests. These checks do not verify visible client input/GUI behavior, Controls-screen keybinding registration, cursor presentation, rendering, or a remote multiplayer session.
- Batching, bounds, allowlists, and thread checks are present in several hot
  paths, but no render-frame/tick-overhead benchmark or before/after
  performance measurement was found. Compatibility documentation describes
  client, GPU, multiplayer, and cross-platform runtime checks as outstanding.

Update this matrix whenever a vertical API slice is added. A new method should
not move a category to “fully implemented” unless its host implementation,
permission/side checks, Rust wrapper, boundary tests, and relevant runtime
verification are all present and described here.
